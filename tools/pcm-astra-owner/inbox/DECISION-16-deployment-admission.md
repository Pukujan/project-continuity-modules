## 1. Selected profile and present disposition

Select one qualification target: **PCM67-WIN32-DELETE-EXTRA-v1**, a single original private installation store, Python 3.12.10 / SQLite 3.49.1, standard Windows VFS, local NTFS storage, rollback journal DELETE and synchronous EXTRA. The research host reports Windows build 26200. These version observations identify a candidate, not an approved stack. The actual VFS/binary identity, NTFS volume and hardware have not been qualified. There is no implicit Windows-wide support or fallback to another filesystem, VFS, SQLite version, WAL, network storage or memory.

Admission requires an exact approved deployment tuple: Python/runtime and SQLite binary hashes, SQLite source ID/compile options, selected VFS and adapter revision, Windows build, filesystem/mount topology, volume/device/controller/firmware/cache configuration, installation/store identity, policy revision and writer deployment revision. No wildcards. The approved tuple set is initially empty. A different tuple requires a separately reviewed qualification record; a familiar version string never supplies the missing evidence.

The supported failure model remains cooperating upgraded writers, one original non-restored store and a storage stack that honors verified locking and durable commit under process death, OS crash and power loss. Undetectable rollback, administrator bypass, credential abuse, cloned installations and concurrent legacy senders are outside that guarantee. If their exclusion cannot be established, admission is UNKNOWN and denied. This design cannot detect a byte-identical rollback by inspecting those same bytes.

## 3. Enrollment, denial and invalidation

Admission is necessary but never sufficient to send. Revalidate its policy/deployment binding before enrollment and before each target consumption. Then require positive READY in the original store, immutable O/I and original pushed SHA S, current actor/issue/lineage authority, complete conflict-free lookup and, for a parent, the independently verified actual leaf comment ID/URL. Atomically compare/update exactly one READY target and durably commit CONSUMED. Only that invocation's successful acknowledgement yields a volatile one-use transport capability; the admission verdict itself never does.

- Initial/default denial performs no enrollment, READY construction, consumption, checkpoint side effects for an automation-requesting invocation, or POST. Report a bounded sanitized reason such as `DURABILITY_UNQUALIFIED`, `PROVENANCE_UNKNOWN`, `WRITERS_UNQUIESCED` or `PROFILE_MISMATCH`. Ordinary manual checkpoint behavior remains a separate existing route.
- If a push already succeeded, report its original SHA as pushed/receipt-pending. Do not roll it back or manufacture a second checkpoint. Missing/corrupt/mismatched stores, rows or qualification records cannot be repaired by recreating READY. Read-only remote reconciliation may verify an existing exact receipt; local absence never authorizes a send.
- A denied pre-consumption gate does not consume or erase existing READY. Once the same original deployment becomes provably eligible, that positive target can be reconsidered with all checks. A denied or uncertain post-consumption outcome never resets CONSUMED, even after HTTP rejection or apparent pre-network failure. It can remain pending indefinitely for manual operational resolution.
- Missing/destroyed store after provisioning, copy/restore/reimage, changed storage/runtime/VFS/adapter configuration, custody uncertainty, or a newly possible legacy sender invalidates admission before any new mutation. Do not transfer/rebind old O to a new store or recover authority by renewing an attestation. A fresh installation can serve only genuinely new operations after fresh qualification. Old operations remain read-only.
- Reconfiguration/revocation must first stop new admissions and quiesce invocations that already earned a capability. A configuration flag cannot retract a live one-use capability. The eventual integration must prevent deployment changes between validation and consumption/send, or deny; no TTL/takeover semantics are introduced.

Store tombstones and immutable intent bindings persist. No import, garbage collection, restore helper, alternate database or automatic retry is authorized. Manual resolution does not reset/re-enroll an operation or waive any release/delivery gate.

Unknown schema/fields, missing evidence, contradictory bindings, invalidation or an unapproved tuple deny. No public `approved=True`, environment override, caller-injected provenance/quiescence booleans, or persistent send flag.

The production evidence provider has **no approved tuples**, so it always denies. Even PASS returns only an admission verdict, never a send capability. No SQLite creation, enrollment, consumption, filesystem repair, Git call, publisher/CLI wiring, transport, credential access, policy approval command or deployment enablement belongs to this first slice. It is useful contract code, not enforcement of today's publisher and not completion of #67.

The bounded test oracle covers all four gates jointly, each gate missing/UNKNOWN/failed/conflicting, exact-tuple drift, store/writer mismatch, copied/restored/legacy disqualification, absent qualification and invalidation.
