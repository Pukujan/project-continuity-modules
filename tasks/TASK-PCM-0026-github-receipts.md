## S1. One optional connection at the real checkpoint boundary

Observable outcome: an opt-in, injected receipt call happens only after the existing checkpoint push returns successfully, and identifies that exact pushed commit. A failed push produces no receipt attempt. Existing callers retain their current behavior.

Extend `publish_checkpoint` with one keyword-only optional `receipt: CheckpointReceiptContext | None = None`. Keep all existing positional parameters and its `str` return. Add a frozen dataclass near the receipt helpers with exactly the caller-supplied fixture/context fields needed here: `repository: str`, `issue_number: str`, `payload_sha256: str`, `bodies: tuple[str, ...]`, `lookup_complete: bool`, and `run: Callable[[list[str], str], subprocess.CompletedProcess[str]]`. Do not provide a default real runner. This internal API is the seam being tested, not a new CLI or a claim that caller-supplied context is authenticated.

When context is supplied, require the existing nonempty checkpoint `request_id`, and reject `recovery=True` before any Git or receipt side effect. Validate the repository/issue syntax through existing `github_issue_comment_path` before Git writes. Do not add a second task ID, request ID, SHA, destination or kind to the context; those must not drift from checkpoint arguments. Without context, preserve recovery, non-GitHub and existing request-ID behavior exactly.

Keep the current Git commit/replay/push sequence intact. Immediately after its existing `git_run(... push ...)` succeeds, construct the v2 marker with the actual `task_id`, actual `request_id`, and the already captured `commit` that was pushed. Derive destination from `receipt.issue_number` and kind as `leaf`. Call existing `publish_issue_receipt` exactly once, with that marker, supplied payload digest, `list(receipt.bodies)`, completeness, repository, issue number, marker as body and the injected runner. Return the same commit on `post` or `recovered`.

The existing `publish_then_receipt` helper is not an integration oracle and need not be called; leave it unchanged. Do not wrap a fake publisher and count that as testing the real checkpoint boundary.

## S2. Ordered effects, recovery and visible partial failure

Receipt lookup/post gating remains owned by the existing helpers. Incomplete or ambiguous lookup must stop the receipt path without a runner call. One exact marker and payload recovers without a POST. A successful Git push followed by any expected receipt failure must be distinguishable from a push failure.

After push success, catch `ContinuityError`, `OSError` and `subprocess.SubprocessError` from the receipt path and raise a sanitized `ContinuityError` containing `CHECKPOINT_PUSHED_RECEIPT_PENDING`, task ID, request ID and exact pushed SHA. Explain that the checkpoint is pushed and the receipt remains unresolved. Do not copy runner stdout/stderr, credentials or local paths into this message or its displayed exception chain. Do not catch process-control exceptions such as `KeyboardInterrupt` or `SystemExit`.

There is no compensating commit, reset, second push, extra POST, recursive checkpoint call or automatic retry. On push failure, propagate the existing error unchanged and never enter the receipt path. A recovered result is successful for this bounded invocation; it is not full issue delivery.

Receipt-only command recovery, durable attempt state, parent reconciliation and the exact user retry command are later scope. This assignment must not invent a command that does not exist or direct users to repeat a checkpoint after a receipt error. State that receipt-only recovery is not yet available through this seam.
